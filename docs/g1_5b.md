# G1.5b: surviving router restarts, choosing when to apply, handles

Applying the registry restarts the cloud router (zenohd 1.10.1 cannot take
a new ACL while it runs: `docs/g1_5.md`). G1.5b makes that restart cheap
for whoever is connected, lets the admin choose when it happens, and names
browser pages after a handle the user chooses.

## A pass belongs to one page

Before G1.5b a pass opened one connection: a page whose connection dropped
(the router restarted on an apply, the line went away) needed a new pass.

Now a pass belongs to the page that uses it first, while it is open:

1. The page makes a random key when it loads (the browser build: 18 random
   bytes, base64url) and keeps it in memory only. It sends the key next to
   the pass on every WebSocket: `wss://<router>/?pass=<pass>&page=<key>`.
2. The first check (nginx `auth_request` -> `/passes/check`) with a live
   pass takes it for that key: the console keeps the SHA-256 of the key
   (`page_digest`) and the time the pass closes (`open_until`, the first
   connection plus `ASTERISM_PASS_LIFETIME`, 4 hours by default). One
   UPDATE takes it, so two pages racing for one pass cannot both win.
3. While the pass is open, a check with the same pass and the same key is
   let through again (`uses` counts the connections). Another key, no key,
   or a pass that closed or was revoked gets 401. A reload is a new page
   (a new key): it needs a new pass.
4. A 204 carries `X-Asterism-Until` (Unix seconds); nginx hands it to the
   door (`auth_request_set`, `proxy_set_header X-Asterism-Until`), which
   closes the connection then, and after `WS_DOOR_MAX_SECONDS` at most. So
   no connection outlives its pass.
5. A page that sends no key (an older build) gets one connection, as
   before.
6. While zenohd restarts, the door answers a page that comes in with a
   plain 503 itself. Before G1.5b it closed the connection without an
   answer, and nginx then wrote the request line, **pass included**, into
   the router door's error log ("upstream prematurely closed connection").
   An error log of a server that ran an earlier version may hold such
   lines: clear it when upgrading (they are spent passes, but still).

The pass and the key never reach a log: the pass is in the fragment of the
link (the page's host never sees it), both travel only in the WebSocket's
query over TLS, nginx logs the router door without query strings, and the
console logs `pass: <id> (user <id> (<handle>)) opened a connection again
from <address>`.

The browser build (fmruby-core `wasm/`) tries again by itself after a
lost connection: zenoh-pico opens it again (a try a second), and the
page's WebSocket link spaces the tries after failures (1, 2, 4, 8, 16 s,
then every 30 s). With a pass it gives up after 10 failed tries in a row
(the pass has most likely closed) and says so in its status line.

## Nodes connect again by themselves

The Zenoh bindings under the asterism gem now keep a client session open
when its router goes away and reconnect it, declaring again everything the
session had declared: zenoh-c does it by itself (asterism-zenoh no longer
closes the session when no router is left), and picoruby-asterism-zenoh
turns on zenoh-pico's `Z_FEATURE_AUTO_RECONNECT`. `Asterism.reconnecting?`
is true meanwhile. Measured on zenohd 1.10.1 restarted with `docker
restart`: back about 1 s after the router (`rake test:reconnect` in the
asterism repository). A home router (zenohd) connects again by itself too.

## Choosing when to apply

The confirmation (Admin > Members, "Review and apply") says in large type how many
browser pages, routers and nodes lose the cloud router for a few seconds,
and offers three ways:

- **now**: as before.
- **when nobody is connected**: waits until the bridge (alive) sees the
  cloud router with no browser page, no other client carrying a node, and
  no Asterism node but the console's own. Router links alone (a home
  router with nothing behind it) do not count. Without a live bridge it
  waits (who is connected is not known).
- **at a time**: a date and time in the browser's time zone (the page
  sends its offset); stored in UTC.

The last two make an apply with the status "waiting". Every relay page
(the registry, roles, applies) shows a bar "waiting to apply" with a
button to cancel it. One waits at a time: a new apply cancels the one that
waits. A waiting apply applies the registry as it is when it runs, not as
it was when it was made.

The waiter (`Relay::ApplyWaiter`) is a thread in the console's server
process that looks every 5 seconds. The state is in the database, so a
console that restarts picks a waiting apply up again.

## Handles

A browser page opened from the console joins the network as
`<ASTERISM_BROWSER_NODE_PREFIX><handle>` (`wasm-<handle>`), a second page
of the same user at the same time as `wasm-<handle>_2` and so on. Every
node sees node IDs, so they are made of a name the user chooses, never of
the email address.

- The user chooses it on the account page (Account > Handle). Until then
  "Open the browser build" is not offered; the page asks for a handle.
- Lower case letters, digits and single hyphens, 3 to 20 characters,
  starting with a letter (so `_2` and the like never make another user's
  name). Stored in lower case; unique among the users.
- Changing it: pages open now keep the old name until they close. The old
  handle stays reserved for its owner for `ASTERISM_HANDLE_HOLD_DAYS` (30)
  days: nobody else can take, at once, a name the network and its records
  still know as someone's. The owner can take it back at any time. A
  removed user's handle is held the same way.
- The migration adds the handle empty for everyone: the earlier names made
  from email addresses are not kept, and their `.<id>` suffix is gone.

## Upgrading

`db:migrate` (the console's start runs `db:prepare`): adds the page
binding to the passes, the handles (empty) and the released handles, and
the waiting columns to the applies. Rolling back (`db:rollback:primary
STEP=3`) drops them; waiting or cancelled applies are deleted then.

The nginx server block of the router door gains two lines
(`auth_request_set $asterism_until ...` and `proxy_set_header
X-Asterism-Until $asterism_until;`). Without them the door keeps its own
limit (`WS_DOOR_MAX_SECONDS`) only.
