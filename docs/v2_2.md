# V2.2: one colour per family, shapes for the levels, the registry put away

Stage V2.2 of the console (plan: the V table, V2.2). Done 2026-10-11 and
checked against the Linux sim running asterism_demo, a P4 board running a
ROS 2 app, a CRuby node and the MuJoCo rover over ROS 2.

Before, the three levels of Asterism (node, app, object) were three
greens, hard to tell apart, and the relay registry's halos added a fourth
green, an orange and a red; the registered names that were not here were
scattered around the edge of the drawing. Now a colour only says which
family something belongs to, the levels differ by shape, and the registry
is off by default.

## Colours and shapes

| Family | Colour | Shapes |
|---|---|---|
| Routers | blue | a diamond; router to router a thick blue line |
| ROS 2 | purple | a node is a purple rounded square (its badges as before) |
| Topics | orange | an edge from publisher to subscriber (or a tag with "Topics as nodes") |
| Asterism | Ruby red (`#cc342d`; teal `#00897b` until 2026-10-11). The ROS 2 services badge moved from crimson to slate (`#455a64`) so that red means Asterism only | node: a white box with a solid Ruby red border, its name in bold after a mark of what it runs on. App: a grey dashed box, no fill. Object: a small Ruby red dot |
| everything else | grey | other connections, sessions (with "Sessions as points"), the registry's box |

The marks before a node's name (plain characters, no emoji):

| Mark | Runs on |
|---|---|
| ▣ (U+25A3) | a board: Family mruby on a board, the Linux sim or the browser build |
| ◈ (U+25C8) | CRuby, or any other Ruby process |
| ◎ (U+25CE) | this console |

The network does not say what a node runs on: an Asterism node is a
liveliness token with its name and nothing else. `Bridge::Marks` tells by
the boards' naming: a board names itself after its mDNS name
`fmruby-<6 hex digits>`, the browser build after the ID its page makes and
keeps, `wasm-<6 hex digits>` (since B2), and the sim falls back to `linux`
(the browser build without its page, to `wasm`; fmruby-core's asterism_demo).
Anything else is ◈. A board given
another name in its node file shows as ◈; the node's details say "told by
its name". The console is the bridge's own node, so ◎ is certain.

This console's node is no longer drawn with a dashed black border (dashed
now means an app): the mark and "(this console)" say it.

## The relay registry

"Relay registry" is off by default; the browser remembers the setting
(`localStorage`, as "Sessions as points"). The rewind page has the same
switch and shares the setting. With it on:

- **Marks in the corner.** An Asterism node or a router the registry
  knows gets a small dark disc at its top right corner: a check
  (registered), a bar (disabled in the registry) or a question mark (not
  in the registry). They replace the green, orange and red halos.
- **One box for the names that are not here.** The registered names that
  are not on the network go in one box, "Not connected (registry)",
  instead of each on its own around the drawing. Routers in it are small
  diamonds, clients small rounded squares, in grey.
- **A dashed line to the expected router**, where the registry tells (next
  section). Its details give the reason in "Expected at".

### What the registry can tell about the router

The registry is the cloud router's list: `Relay::CloudConfig` makes the
cloud router's ACL from it, one subject per router or client that is
enabled and has a valid certificate (`in_acl`). So:

| Entry | Expected router |
|---|---|
| a client in the ACL (a machine with a certificate for the cloud router) | the cloud router |
| a router in the ACL (the relay's other end, e.g. the home router) | the cloud router |
| the cloud router's own entry (it holds its server certificate) | none: it is the router |
| an entry left out of the ACL (disabled, no valid certificate) | none: the cloud router refuses it, and the registry knows nothing else |

The cloud router's name is `Relay::Settings.cloud_name`
(`ASTERISM_RELAY_CLOUD_NAME`, default `zenohd-cloud`). The line goes to
the cloud router when it is on the network, to its own entry in the box
when that is registered but not here, and nowhere otherwise.

What the registry cannot tell: which LAN router a client uses when it is
at home (a client on the LAN joins the home router over plain TCP, which
the registry does not cover), whether a client comes through the home
router's relay or straight to the cloud, and anything about ROS 2 peers
(their certificate names are not node names, so they never match a node).
Those entries only sit in the box. For the names that are here, the line
they really use is drawn as before; the expected router is not drawn.

## Where it is built

`lib/bridge/marks.rb` (`Bridge::Marks.apply(graph, cloud:)`), called at the
end of `Bridge::Graph#to_h` after `Bridge::Connections`, and by
`RecordingsController#graph` for the rewind. It sets data `machine` on the
Asterism nodes, adds the `reg_box` node (the registered names get it as
their `parent`, and data `expect` when the registry tells) and the
`expect` edges. It removes what it added before adding it again, so
recordings made before V2.2 get the same drawing (their registered names
lack nothing it needs: kind and `in_acl` were recorded since W2).

The page (`console_controller.js`) only chooses what to show:
`REGISTRY_KINDS` (`reg_box`, `registered`, `expect`) follow the registry
layer, and the corner mark is drawn while the layer is on. A registered
name that comes onto the network leaves the box and its node gets a mark;
one that leaves goes into the box (the live diffs move nodes between
parents).

## Legend

The kinds with their shapes (white box with teal border, grey dashed box,
teal dot, ...), the three marks before the names, the lines; with the
registry on, also the box, "Registered, not connected", "expected router

graph leave out the registered names while the registry is off.
