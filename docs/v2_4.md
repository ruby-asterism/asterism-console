# V2.4: a frame around an open machine, and the gateway's address

Stage V2.4 of the console (plan: the V table, V2.4). Done 2026-10-11 and
checked against the MuJoCo rover over ROS 2 (10 nodes from its container),
a P4 board running a ROS 2 app and a CRuby ROS 2 node (`ros2_talker.rb`),
both through zenohd's port published on the LAN, the Linux sim running
asterism_demo, and a recording made before V2.4.

V2.3 folded the ROS 2 nodes of one machine into one box and drew them one
by one when opened, with nothing around them: once open, which nodes were
the rover's was not visible any more, and they could end up spread among
the others. And every device that reached zenohd through Docker's
published port came from the same address, so two boards on WiFi were
folded into one "machine".

## The frame of an open machine

An open machine's nodes are drawn in a frame: a purple rounded rectangle
around them with the machine's name (or IP) and its node count above its
top left corner.

- **How it is drawn.** Not a compound node: V2.1 tried a box around a
  process and fcose let it swallow the drawing (docs/v2_1.md). The frame is
  a node of its own (class `frame`, kind `frame`, id `frame:<group id>`)
  that no layout sees (`visible()` leaves it out, and so the layouts, the
  counts and the view fitting), drawn under everything, edges included
  (`z-compound-depth: bottom`), not selectable or grabbable. Its size and
  place are data (`fw`, `fh`) computed in the page (`syncFrames`): the
  bounds of the machine's shown nodes (each node's shape, its label and its
  badge, not the badge's `bounds-expansion`, which is only for the
  renderer) plus 14 px.
- **When it is redrawn.** On every `position` event of a node with a
  `group` (a drag, a layout, a node placed), coalesced to one redraw per
  browser frame (`queueFrames`), and at the end of every `applyView` (a
  machine opened or folded, a layer switched, a diff applied: nodes joining
  or leaving the machine). A frame whose machine is folded, gone, or has no
  node shown is removed. Folding a machine removes its frame.
- **Clicking** the frame or its name (`text-events: yes`) selects the
  machine: its details as in V2.3, with "Fold". The frame of the selected
  machine has the selection's amber border.
- The nodes inside stay free: they can be dragged, in and out; the frame
  follows. Nothing stops another node from being dragged into a frame.

## Keeping a machine together (layout)

- **"Lay out again" and the first graph** (`layoutAll`): each open
  machine's nodes are laid out on their own first (fcose on the nodes and
  the edges among them only, from a ring, shorter ideal edges); that gives
  the shape and size of the machine. Then the whole graph is laid out with
  those machines folded and each machine's box as large as its nodes need
  (style bypass on the `r_group` node), so the layout keeps the other
  nodes out of that room. Then each machine's nodes go where its box went,
  in the shape from the first step, and the boxes are folded away again.
- **Opening a machine for the first time** (`openGroup`): its nodes are
  laid out on their own as above and put where the folded box was; the
  other nodes keep their places, except those that are now in the frame
  (with 24 px of room), which move out of it the shorter way from its
  middle and on in that direction until they overlap nothing
  (`clearFrame`). An Asterism node moves with its apps and objects.
- **A node that arrives later** (a diff, a step of the rewind) is placed
  next to its neighbours as before; if that is inside an open machine's
  frame and it is not one of the machine's nodes, it is moved out the same
  way.
- Other nodes can still come to lie in a frame (dragged, or fcose's
  placement of new nodes next to the frame); it is not prevented, only made
  unlikely.

## The gateway's address

Through Docker's published port (Docker Desktop, and WSL), every LAN
device and every host process reaches zenohd from the Docker network's
gateway (e.g. `172.20.0.1`): the address says nothing about the machine.
The ROS 2 nodes from a gateway's address are **not folded**: each is drawn
by itself, as a node alone at its address is. Its details say, on the
"Machine" line, that the machine is not known because the address is a
gateway, and how that was found.

How the console knows a gateway (`Bridge::Gateways`, lib/bridge/gateways.rb):

- **Seen in the graph** ("detected"). The bridge knows its own end of its
  link to the router (`Session#links`, `src`, e.g. `tcp/127.0.0.1:38722`),
  kept as the router's data `bridge_link.local`; the router's admin space
  says where the bridge's sessions come from (the session's `address`,
  e.g. `tcp/[::ffff:172.20.0.1]:42320`). When the two IP addresses differ,
  something between rewrites the source address, and the address the
  router sees is a gateway **at that router**. The bridge reaches zenohd
  the way the LAN does in the setup this console runs in (the published
  port), so nothing has to be set. Recordings keep `bridge_link.local`
  (it is in the router's data), so their rewind finds the gateway the same
  way.
- **Configured** ("given"): `ASTERISM_GATEWAY_IPS`, comma or space
  separated, taken at every router. For the setups where the bridge does
  not go through the gateway the devices use: the bridge in a container on
  the Docker network, on another host, or a router behind a NAT the bridge
  is not behind.
- **A recording made before V2.4** has no `bridge_link.local`: its rewind
  takes the configured gateways and the ones the live graph shows today
  (as names are today's in V2.3).

Where neither tells (the bridge's address is not rewritten and nothing is
configured), nothing is a gateway and nodes fold by address as in V2.3. A
setup with no address rewriting (zenohd on the host network, or Linux
Docker where the published port keeps the client's address for LAN
traffic) needs nothing: the devices arrive with their own addresses.

Why not the other ways the instruction listed: zenohd's admin space does
not say what its addresses are behind (it lists its locators, e.g.
`tcp/[::]:7447`, and the peers' addresses as it sees them), and asking
Docker for the network's gateway would tie the console to the Docker CLI
and its socket, and would be wrong for a bridge that reaches zenohd some
other way.

## Where it is built

- `Bridge::Gateways`: `configured(env)`, `detect(graph)` (`{ router id =>
  [ip] }`), `detected_ips(graph)`.
- `Bridge::Groups.apply(graph, names:, gateways:)`: a ROS 2 node whose
  first session's (IP, router) is a detected gateway, or whose IP is in
  `gateways`, is left out of the groups and gets data
  `gateway: { "ip", "how" => "detected" | "given" }`. Idempotent like the
  rest (it removes `gateway` before deciding again).
- `Bridge::Graph.build(..., gateways:)` and `Graph.derive(..., gateways:)`
  pass it through; the bridge passes `Gateways.configured`, and
  `RecordingsController#graph` passes the configured and, for an older
  recording, today's.
- The page: the frame (`syncFrames`, `queueFrames`, `frameBounds`,
  `clearFrame`), the layout (`layoutAll`, `layoutMembers`, `openGroup`,
  `openMembers`), and the "Machine" line of a ROS 2 node's details.
