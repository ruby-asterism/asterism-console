# O1: a console anyone can install on their own server

The console started as one person's tool next to one router. O1 makes it
something anyone sets up on their own server, with one domain name, from
the published image and the general steps of [install.md](install.md):
their own Asterism network, under their own rules. This note says what
changed for that and why.

## 1. Nothing assumes one particular network

What was taken out of the defaults, the pages and the code:

| Before | Now |
|---|---|
| A node without a profile was marked "Family mruby" when its name looked like one family of boards (`fmruby-<hex>`, `wasm-<hex>`, `linux`, `wasm`) | Nothing is guessed from a name: no profile, no mark (`machine_by: "none"`). The profile's kinds (`family_mruby`, `picoruby`, `cruby`, `console`) stay: they are the network's vocabulary, told by the nodes themselves |
| Passes linked to one particular page (`ASTERISM_STUDIO_URL`) | A page is an integration configured by `ASTERISM_BROWSER_PAGE` (a URL template); without it, passes are shown alone. `ASTERISM_STUDIO_URL` is no longer read |
| Apply ran `docker compose -f docker-compose.yml -f docker-compose.relay.yml restart zenohd-cloud` in the directory above the checkout (one development workspace) | Apply runs `bin/relay_restart_request` (a request file next to the generated configuration, which the router's container watches), or the command in `ASTERISM_RELAY_RESTART` |
| The compose file named the router `zenohd-vps` | `zenohd-cloud` (`ROUTER_NAME`) |
| The server's steps assumed one provider's packet filter, one layout under `/opt`, a systemd template unit and nginx 1.18 | install.md: any Linux server with Docker; nginx, Caddy and a systemd unit are examples; the firewall notes are general (docker's published ports and ufw, IPv6) |
| One app for every player (`game`, from G0) | Already gone in G1.5 (roles name their apps); "match" is only the example role the setup adds |

Kept on purpose: the browser node prefix `wasm-` (`ASTERISM_BROWSER_NODE_PREFIX`;
a WebAssembly page's IDs, settable), the example role "match" (a starting
point the admin changes or removes), and the design notes of earlier
stages in `docs/` (they record how it was built and tested, including with
Family mruby boards and browser builds).

## 2. The steps (install.md)

One document from an empty server to a working network and back: the
server, DNS, `.env`, the first setup, the start, the web server and TLS,
the firewall, the first sign-in, the first router and node, browser pages,
checks, backups, updating, rolling back, stopping, building the image
yourself, starting with the server, updating an earlier deployment and
troubleshooting. Values that are yours appear only in `.env` (and in the
web server's files, which are examples).

The rehearsal of the same steps on one PC is `deploy/local/` (an nginx
container in place of the server's web server, names under `.localtest`,
a project name of its own).

## 3. A published image per version

- `VERSION` holds the console's version (0.1.0 first), shown on the account
  page and by `bin/asterism version`; `CHANGELOG.md` says what each version
  needs.
- `.github/workflows/image.yml`: a tag `v<VERSION>` builds
  `deploy/vps/Dockerfile` for linux/amd64 and linux/arm64 (QEMU on the
  runner) and pushes `ghcr.io/ruby-asterism/asterism-console:<version>`,
  `:<major>.<minor>` and `:latest`. The tag must equal `VERSION`. A run by
  hand builds without pushing.
- `deploy/vps/docker-compose.yml` pulls `${CONSOLE_IMAGE}:${CONSOLE_VERSION}`
  (`ghcr.io/ruby-asterism/asterism-console:0.1.0` by default). An update is
  `CONSOLE_VERSION` in `.env`, `docker compose pull`, `up -d`; the console
  migrates its databases when it starts. `docker-compose.build.yml` builds
  the image on the server instead.
- Rolling back across a migration means restoring the data backed up
  before the update (migrations are not undone by an older image).

## 4. The first setup in one command

`docker compose run --rm console bin/asterism setup` runs in the console's
container next to the signer and does, only what is not done yet:

1. checks `.env` (secrets, names, placeholders left in, the enrollment mode);
2. `db:prepare`;
3. the CA: the signer now starts without one and makes it when asked
   (`POST /init`, once; 409 when there is one). The key stays in the
   signer's volume; the console only sees the certificate. An existing CA
   is still imported with `bin/signer import` before the setup;
4. the example role "match" (when there is no role);
5. the first admin (`ADMIN_EMAIL` / `CONSOLE_PASSWORD`, or asked on the
   terminal);
6. the server's own certificates (the router's, valid for the public name
   and for `zenohd`, and the bridge's), issued again when missing, from
   another CA, within 30 days of their end, or not naming the public name;
7. the router's configuration from the registry.

Running it again changes nothing that is in place, so the same command
also follows an update.

**How people get in** is a setting, `ASTERISM_ENROLLMENT`. Only `admin`
exists: an admin registers every router and node and invites every user.
Planned, not built: `approval` (people ask, an admin approves) and `self`
(people add their own nodes within limits set by roles); the console
refuses to start with them.

## 5. Certificates as one file

The certificate page keeps its three "Save to file" buttons and adds
**"Save all (.tar)"**. The tar is made in the browser
(`app/javascript/lib/credentials_tar.js`, POSIX ustar, no compression),
because the key is made there and never sent: making the archive on the
server would hand the key to it.

```
<name>/                 0755
<name>/<name>.key       0600   the private key (PKCS#8)
<name>/<name>.pem       0644   the certificate (CN = name)
<name>/ca.pem           0644   the CA
<name>/zenoh.json5      0644   a router: a home router's whole configuration
                               (listen tcp/7447 for the LAN, connect to the cloud
                               router with mutual TLS, relative paths: runs as it is
                               where it is extracted); a client: the connection
                               for any zenoh client
<name>/asterism.json    0644   {"format": 1, "name", "kind", "router", "serial",
                                "not_after", "fingerprint", "console", "issued_at"}
```

The entries sit in one directory so that extracting never mixes two
peers' `ca.pem` or keys. `asterism.json` holds nothing secret; the console
makes it (with the router's public locator and its own URL) and the
browser puts it in the tar.

**CRuby** connects with the file alone: `Asterism.connect(credentials:
"alice.tar", app: "game")` (also `Asterism::Zenoh.open` and
`Asterism::ROS.connect`; the asterism gem after 0.7.0). The gem reads the
tar in memory with Ruby's own tar reader, gives zenoh the three PEMs as
`transport/link/tls/*_base64` with `enable_mtls`, takes the router and the
node ID from `asterism.json` unless given, checks that the key belongs to
the certificate, and warns, as ssh does, when the file can be read by the
group or others.

**A home router** extracts the file and runs `zenohd -c zenoh.json5` in the
directory (or the official image with `-w`). Boards' TLS (zenoh-pico) is
for a later stage.

## 6. The web server

The console needs two things from the web server: HTTPS (with
WebSockets) for itself, and, for browser pages, a check of the pass before
a WebSocket opens, with the query dropped before the door and the logs. The
pass check now reads the original URI from `X-Original-URI` (nginx's
`auth_request`) or `X-Forwarded-Uri` (Caddy's `forward_auth`). The Caddy
example runs the check, the query removal and the proxy in that order
(`route`); `uri query -pass` outside a `route` runs before `forward_auth`
and the check never sees the pass.

## 7. What stays for later

- Enrollment by approval and self-service (G2), on the `ASTERISM_ENROLLMENT`
  setting.
- Boards with TLS of their own (how they take the credentials).
- The development Gemfile still takes the Asterism gems from checkouts next
  to this repository unless `ASTERISM_GEMS=rubygems`; the image uses
  rubygems.org.
