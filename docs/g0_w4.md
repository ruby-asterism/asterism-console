# G0 / W4: the internet router and the console on the web

The console and an Asterism router on a server that anyone on the internet
can reach, guarded so that taking the address limits off does not open
anything: the router asks for a certificate (or, for browsers, a pass the
console gave), the console for a sign-in, and the admin pages for an
admin's address. Setting it up: `deploy/vps/README.md`; the same layout on
one PC: `deploy/local/README.md`.

## One console, on the server

The console on the server is the console: the registry, the ACL, the
users and the certificates live there. Its signer (`bin/signer`, the CA's
private key) runs next to it, in a container of its own with the CA in a
volume nobody else mounts, reachable only from the console over an internal
network. A console on a PC stays useful as a development tool (fixture
mode, a local network), but the registry of the internet router is the
server's.

## Certificates: the key is made in the admin's browser

"Issue a certificate" on a peer's page makes an ECDSA P-256 key pair with
the browser's Web Crypto, sends only the public key (SubjectPublicKeyInfo),
and the signer signs a certificate for it (the same name, SANs and
extensions as before: CN = the peer's name, serverAuth and clientAuth).
The page then shows the private key (PKCS#8 PEM), the certificate, the CA
and an example configuration once, with "Copy" and "Save to file". Leaving
the page asks first and loses the key; it cannot be shown again (revoke and
issue again). The console never sees a private key: the request has no
place for one, a private key sent by mistake is refused, the page and the
answer are `Cache-Control: no-store`, and the public key and the PEM bodies
are filtered from the request log. The page needs a secure context (https,
or localhost) and says so otherwise.

A public key alone proves nothing about who holds the private key, and
needs not: a certificate is no use without that key, and only an admin can
ask for one.

The server's own identities (the router's and the bridge's certificates)
are made on the server by `bin/rails relay:issue_local`: their keys live
there anyway.

The previous download (a tar with a key made by the console) is gone. The
route is the same (`POST /admin/relay/peers/:id/certificates`) and now
takes `{"spki": "<base64 DER>"}` and answers JSON; nothing else used the
tar.

## The ACL of the internet router

Made from the registry (`lib/relay/cloud_config.rb`), default deny. On top
of the per-peer read-write and read-only keys of W2:

**Roles** (since G1.5, `docs/g1_5.md`). G0 had one fixed set of rules for
"players" (a peer with a "Player" tick, for one app set by
`ASTERISM_RELAY_GAME`). They are now a role, "match", one of any number of
roles an admin writes as key templates; a row of the registry picks roles,
and `${node}` in a template stands for each node the row speaks for (its
own name, or for a home router the nodes behind it, "Nodes it speaks
for"). "match" keeps G0's meaning, with calls narrowed to the caller's own
name:

| Section of the role | Messages | Direction | Keys ("match", app `game`) |
|---|---|---|---|
| read and write | all nine | both | `asterism/${node}`, `asterism/${node}/game/**`, `asterism/${node}/@profile` |
| read | declare_subscriber, liveliness_query from it; all nine to it | | `asterism/*`, `asterism/*/game/**`, `asterism/*/@profile` |
| ask | query | from it | `asterism/*/@profile`, `asterism/*/game/*/meta`, `asterism/*/game/*/call/${node}` |
| watch | declare_liveliness_subscriber | from it | `asterism/**` |

- A node writes (puts, declares queryables and liveliness tokens) only at
  its own nodes. It reads the app of every node and calls it under its own
  name only.
- The watch is needed because the asterism gem declares one liveliness
  watch on `asterism/**` (on_join / on_leave); zenohd 1.10.1 refuses a
  declaration wider than what is allowed as a whole. What reaches the watch
  is still cut on the way out by the read rules: other apps' tokens (a
  `demo` app at someone's home) never leave their side.
- Everything else (`demo`, `fmrb`, ROS 2, the admin space `@/**`) is denied
  unless a role or the row's own keys add it.

**Browsers** (`ASTERISM_RELAY_BROWSERS=ws/[::]:7449`): the router's ws/
listener sits behind nginx, which lets a WebSocket through only with a live
pass. zenohd cannot tell one browser from another (no certificate, and
zenoh-pico has no user / password), so all ws/ sessions are one subject
(`link_protocols: ["ws"]`) with the roles marked for browsers, `${node}`
being `wasm-$*` (`ASTERISM_BROWSER_NODE_PREFIX`, the browser build's IDs).
A browser cannot write at another row's node, but one browser can write at
another browser's `wasm-*` node (docs/g1_5.md: what would close that).

**Connection limits** (`transport/unicast`, names checked against zenoh
1.10.1): `max_sessions` 64 (every session at the router, all kinds),
`accept_pending` 16, `accept_timeout` 5000 ms; `transport/link/rx/max_message_size`
4 MiB. nginx adds per-address limits for the wss door (30 opens a minute,
8 at once).

## Browser passes

1. A signed-in user presses "Make a pass" (Browser passes). The console
   keeps the pass's SHA-256 only, with who made it, when, and from where,
   and shows the pass once with a link to the browser build
   (`?zenoh=ws/router.example.org:7443#zenoh_pass=<pass>`: the pass is in
   the fragment, which the browser never sends to the server that serves
   the page, so that host's access log does not see it). A pass belongs to
   ONE page (G1.5b; before it, G1: one connection): the first successful
   check takes it for the page that made it (the page's own key, below);
   that page may connect again with it while the pass is open (4 hours
   from the first connection, `ASTERISM_PASS_LIFETIME`), every other page
   gets 401. It must be used within 10 minutes
   (`ASTERISM_PASS_TTL`); a user has at most three live passes (older ones
   are revoked); the owner or an admin can revoke one.
2. The browser build (G1) reads `#zenoh_pass=` (and the older
   `?zenoh_pass=`) in the first script of its page, takes it out of the
   address bar at once (`history.replaceState`), keeps it in memory only,
   and connects to `wss://router.example.org:7443/?pass=<pass>&page=<key>`
   (never on `ws://`). The key is random, made when the page loads, kept in
   memory only (G1.5b): a reload is a new page.
3. nginx (`deploy/vps/nginx/asterism-router.conf`) asks the console with
   `auth_request` before it opens each WebSocket: the subrequest carries
   the original URI in `X-Original-URI`, the console answers 204 (live, or
   open for this page) or 401 (none, unknown, another page, used, closed,
   expired, revoked) and counts uses and refusals. A 204 says until when
   the pass is open (`X-Asterism-Until`), which nginx hands to the door.
   One UPDATE takes the pass, so two checks racing for it cannot both
   win; only the SHA-256 of the page's key is kept. The console's public server block does not pass
   `/passes/check` on (404).
4. nginx drops the query before proxying (`rewrite ^ /? break;`; the check
   reads `$request_uri`, which the rewrite does not change), so nothing
   behind nginx sees the pass. The upstream is the door relay
   (`bin/ws_door`, the `door` service), which forwards to zenohd's ws/
   listener and logs the path it got (and whether it carried a query; the
   query itself is never logged).
5. **Connection lifetime.** nginx's proxy timeouts only close an idle
   connection, and a Zenoh session is never idle (keep-alives), so the door
   closes every connection when its pass closes (`X-Asterism-Until`) and,
   at most, when it is `WS_DOOR_MAX_SECONDS` old (4 hours by default). A
   connection that is open stays open until then, also after its pass is
   revoked (the router has no way to ask again); closing the page ends it
   earlier. A page that loses its connection (the router restarted on an
   apply, the network dropped) connects again by itself with the same pass
   while the pass is open (G1.5b, `docs/g1_5b.md`); after that the user
   opens a new page from the console.
6. The pass is in the WebSocket URL, so nginx logs the router door without
   query strings (`asterism_noquery`), and the console's request log has
   only `/passes/check`.

**One connection per pass, and pages that open two.** The Family mruby
apps that used Asterism and a plain Zenoh session (othello, rt_probe, the
rover pilot) opened two WebSockets, and the second was refused with a
one-time pass (checked in the rehearsal, G1). Settled in G1b
(`docs/g1b.md`): with asterism 0.6.0 an application puts, subscribes and
runs its ROS 2 node on the object layer's own session (`Asterism.session`),
so each opens one connection and one pass is enough. (G1.5b: a pass now
belongs to one page, which may connect again; a page that opens two
connections at once still gets one.)

## The console on the web (W4)

- **Roles**: signed out (the sign-in page only), user (invited: the graph,
  plots, logs, their own call log, passes, permitted calls), admin (the
  admin pages and recordings).
- **No sign-up**: an admin makes an invitation (Admin > Users): a link with
  a one-time token (only its SHA-256 is kept), good for 72 hours, used once;
  an invitation can make an admin. `bin/rails console:user` still works on
  the server.
- **Sign-in limits**: Rails, 10 tries per address in 3 minutes and 20 per
  email address in an hour (`RateLimits::STORE`: the cache store in
  production, a memory store elsewhere); nginx, 10 a minute per address
  (burst 5) on `/session` and `/invitations/`.
- **TOTP for admins**: with `CONSOLE_ADMIN_TOTP=required` (the default in
  production) an admin without a second factor reaches only the account
  page (to turn it on) and sign-out, and cannot turn it off.
- **The admin pages** are all under `/admin`: the relay registry,
  certificates and apply (`/admin/relay/...`), the call permissions
  (`/admin/call_permissions`), the users and invitations (`/admin/users`,
  `/admin/invitations`) and every pass (`/admin/passes`). nginx limits
  `/admin` by address (`asterism-admin-allow.conf`), and so does the
  console with `CONSOLE_ADMIN_NETS`. Recordings and playback (`/recordings`,
  `/playbacks`) are admins' too, by role (and `CONSOLE_ADMIN_NETS`), not by
  nginx. The graph asks which permissions cover an object at `/permissions`
  (every user). Machine names (V2.3) are changed by admins at
  `/machine_names` (by role).
- **Production settings**: HTTPS only (`force_ssl`, HSTS), the session cookie
  `Secure`, `HttpOnly`, `SameSite=Lax`; `CONSOLE_HOSTS` for host
  authorization and the Action Cable origin; a content security policy (no
  inline scripts but the import map's, by nonce; styles from the origin,
  Turbo's progress bar by hash, style attributes allowed; images from the
  origin, data: and blob:; no framing, no plugins); the passes, keys,
  certificates, codes and passwords filtered from the log.
- **Heavy values**: the watch panel sends at most 10 values a second per
  key, and a value over 16 KB (a camera picture) at most 2 a second
  (`ASTERISM_WATCH_HEAVY_RATE`).

## What it does not do (yet)

- A browser's node is not tied to its pass's user: every browser may write
  at any `wasm-*` node.
- zenohd 1.10.1 has no revocation list: a disabled peer's certificate still
  opens TLS until it expires; the ACL denies it everything.
- The home router's own admin space is not read through the internet router
  unless its peer has "Console can see behind this router" ticked (the
  registry's `admin_space`, on by default for a new router), so the graph
  shows it as `router <zid>` without its name.
- The registry's names are shown to every user in the graph's "Relay
  registry" layer.
- `CONSOLE_ADMIN_NETS` also covers recordings (they need an admin), so an
  admin away from those networks cannot see them either.
