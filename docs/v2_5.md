# V2.5: what a node says it is, and its icon

Stage V2.5 of the console (plan: the V table, V2.5). Done 2026-10-12 and
checked against the Linux sim, the browser build, an AtomS3R board and a
P4 board (older firmware), CRuby nodes of asterism 0.5.0 and 0.4.1, and
the console's own node.

Until V2.4 the console guessed what an Asterism node runs on from its name
(`fmruby-<6 hex>`, `wasm-<6 hex>`, `linux`, `wasm`: a board; anything else:
CRuby; V2.2). asterism 0.5.0 lets a node tell it: its **profile**
(`Asterism.profile`, answered on `asterism/<node>/@profile`) says what
Ruby runs it (`kind`), where (`host`), a display name (`name`) and an icon
(a PNG of up to 8 KB and 256x256, with its `icon_hash`). The console asks
each node once and draws what it is told.

## What the graph shows

| | A node with a profile | A node without one (asterism 0.4.x, older firmware) |
|---|---|---|
| Mark before the name | from its kind | from its name, as in V2.2 |
| Icon | before the mark and the name (above the box when the node holds apps, below it otherwise) | none |
| Details, "Runs on" | the kind, "told by its profile" | the guess, "guessed from its name: no profile" |
| Details, "Name", "Host", "Icon" | when the profile has them (the icon at 32x32 with its hash) | not shown |

The marks are named after the Ruby that runs the node (they said "board"
and "CRuby" before):

| Mark | Kind | Runs on |
|---|---|---|
| ▣ (U+25A3) | `family_mruby` | Family mruby: a board, the Linux sim or the browser build |
| ▤ (U+25A4) | `picoruby` | PicoRuby (or mruby) with the asterism mrbgem |
| ◈ (U+25C8) | `cruby` | CRuby; also the guess for a node without a profile whose name is not a board's |
| ◎ (U+25CE) | `console` | a console (this one, always) |
| ◇ (U+25C7) | anything else | another kind a profile told (shown by its name in the details) |

The display name is in the details only: the graph keeps the node ID as
the node's name, so the same node is found by the same name everywhere
(calls, permissions, the registry).

The icon is a background image of the node (cytoscape cannot put an image
in a label), placed left of the label by the label's measured width
(`applyIcons` in `console_controller.js`, a style bypass). With the relay
registry on, the registry's corner mark is the second image of the same
node.

## How the bridge learns the profiles

`lib/bridge/profiles.rb` (`Bridge::Profiles`), driven by `Bridge::Runner`:

- **A node that appears** (a new name among the `asterism/**` liveliness
  tokens) is asked once, on a worker thread of its own:
  `Asterism.profile_of(node, icon: false)`, the profile without the icon
  bytes. When its `icon_hash` is not in the icon store, it is asked again
  with the icon, and the icon is kept by its hash.
- **The icon store** is a table, `node_icons` (`NodeIcon`: hash, PNG,
  width, height). Every node with the same icon shares one row, so an icon
  crosses the network once per icon, not once per node (ten boards with
  the firmware's icon: one fetch). The rows stay after the nodes leave.
  The page loads them from `/icons/<hash>` (signed-in users; cached by the
  browser, a hash names one icon for good).
- **Notices**: a node of asterism 0.5.0 puts its profile without the icon
  on `asterism/<node>/@profile` when it connects and on each change. The
  bridge subscribes to `asterism/*/@profile`; a notice replaces what is
  known about that node, and fetches the icon when the hash is new. So an
  application that changes its name or icon is redrawn at once. When
  several applications of one board answer differently, the last notice
  wins.
- **No answer** (asterism 0.4.x, or a node gone meanwhile): the node keeps
  the V2.2 mark; it is not asked again until it leaves and comes back. A
  query to such a node ends at once (nobody answers the key), so the worker
  does not wait.
- **A node that leaves** is forgotten and asked again when it comes back.
- **Checks**: what comes from the network goes through
  `Asterism::Profile.check` (the gem's): only `kind`, `host`, `name`,
  `icon`, `icon_hash`, each checked; an icon that is not a PNG, is larger
  than 8 KB or 256x256, or whose chunks do not run from IHDR to IEND is
  dropped with its hash. SVG is never accepted (it can carry scripts).
- **This console's own profile**: `kind: console`, with the icon
  `app/assets/images/asterism_console.png`, set before the bridge connects
  and kept in the store, so the console's node shows it too.

The graph carries the profile (without the icon) on the node, data
`profile`; `Bridge::Marks` turns it into data `machine` (the kind),
`machine_by` (`profile`, `name` or `self`) and `icon` (the URL, when the
store has that hash).

## Recordings and the rewind

The recorded network structure (V4) already holds the graph as the page
gets it, so a recording made with V2.5 has each node's profile, without
the icon bytes. The rewind gives the marks from the recorded profiles and
takes the icons from **this console's store** by their hashes
(`RecordingsController#rewind_icons`). Chosen over putting the icons into
the MCAP file: the file stays as it was (no new channel), and an icon is
stored once whatever the number of recordings. The cost: a recording
opened on another console, which never saw that icon, shows the marks
without the icons. Recordings made before V2.5 have no profiles and get the
marks by name, as before.

## The live check (2026-10-12)

The network: zenohd (the main compose with the LAN and ws overlays), the
Linux sim and the browser build running asterism_demo (built with
asterism 0.5.0 and Family mruby's default profile), an AtomS3R board on
WiFi running asterism_demo on a new firmware, a P4 board on WiFi running
asterism_demo on an older firmware (asterism 0.4.0), a CRuby node of 0.5.0
(`cruby`, display name "Lab PC") and one of 0.4.1 (`oldcruby`).

| Node | Drawn as | Details |
|---|---|---|
| this console | console icon, ◎ | console |
| `linux` (sim) | Family mruby board icon, ▣ | told by its profile, host `sim` |
| `wasm-<6 hex>` (browser) | browser icon, ▣ | told by its profile, host `browser` |
| `fmruby-<6 hex>` (AtomS3R, new firmware) | board icon, ▣ | told by its profile, host `atoms3r` |
| `fmruby-<6 hex>` (P4, older firmware) | no icon, ▣ | guessed from its name: no profile |
| `cruby` (0.5.0) | ruby icon, ◈ | told by its profile, name "Lab PC" |
| `oldcruby` (0.4.1) | no icon, ◈ | guessed from its name: no profile |

- **Changes reach the graph.** asterism_demo's `info.profile(name,
  own_icon)` (and its key `p`) sets a display name and the app's own icon.
  Called on the sim from the PC, the bridge got the notice, fetched the new
  icon once (591 B) and the graph showed it with the name in the details
  within a second; back to the default, the old icon came from the store
  without a fetch. On the browser build the same switch fetched nothing:
  the app's icon was already in the store.
- **Registry layer on**: the icon and the registry's corner mark on the
  same node.
- **Rewind**: a recording of the structure while the sim's profile was
  switched back showed the name and the app's icon at the start and the
  default icon at the end.
