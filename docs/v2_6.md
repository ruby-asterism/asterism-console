# V2.6: a node reached through a router the console cannot read

Stage V2.6 of the console. Done 2026-10-13; tested with made-up IDs
(`test/lib/bridge/graph_test.rb`, `test/lib/bridge/connections_test.rb`),
not yet looked at on a live network.

The graph's lines between nodes and routers come from the routers' admin
space: each router lists its sessions (`@/<zid>/router`) and which session
declared each token (`@/<zid>/router/token/**`). When the console reads
only some of the routers (a relay: the cloud router's ACL lets the console
read its own admin space, and a home router behind it is not readable,
e.g. a registry router without "Console can see behind this router"), a board at the home
router used to float with no line at all: no readable router has its
session.

The cloud router's token table does say where the board's tokens came
from. Its entry lists the router that delivered them under "routers":

```
@/<cloud zid>/router/token/asterism/fmruby-aaaaaa/game
  {"routers":["<home router zid>"],"peers":[],"clients":[]}
```

## The via edge

`Bridge::Graph#link_tokens` now reads "routers" as well. A node gets a
`via_router` edge, node -> router, label `via`, when:

- no readable router carries it (it has no `carries` edge, so no `attach`
  edge in the default drawing), and
- a readable router's token table lists one of its tokens (Asterism:
  `asterism/<node>/...`; ROS 2: its `@ros2_lv/...` tokens) under "routers"
  with a router that is in the graph (a router node, from a router link or
  a linkstate).

The router that lists the token is never taken for itself. When the
routers named include some whose admin space is not readable, only those
get an edge (a readable one would have carried the node). One edge per
node and router, however many tokens name it. A router ID that is not in
the graph gives nothing. When the home router's admin space is readable
the node has its `carries` edge and the drawing is exactly what it was
before V2.6.

The edge means "reached through this router; what is behind it is not
visible". On the page it is a dashed, lighter grey line labelled `via`,
shown in the default drawing and with "Sessions as points" alike; the
legend has a line for it whose tooltip, like the edge's details (click
it), says the router's admin space is not readable (for a router in the
relay registry: tick "Console can see behind this router"). With the registry layer, the node's
"Through" in its details names that router too (data `via`).

## Where it is built

| Part | |
|---|---|
| `via_router` edges | `Bridge::Graph` (lib/bridge/graph.rb): node -> router, label `via`. Kept as they are by `Bridge::Connections` (the node has no `attach` edge and empty `connections`), folded by `Bridge::Groups` like the other node edges |
| style, legend, details | `console_controller.js` (`EDGE_COLORS.via_router`, `VIA_HINT`) |

Recordings carry the edge in their graphs like any other; a recording made
before V2.6 has none (the rewind does not rebuild it: the token tables are
not recorded).

## The registry setting behind it

The registry's `admin_space` flag is an entry in the cloud router's ACL,
not a setting of the peer: it never reaches the peer's own configuration.
The pages name it by what it lets the console see:

- A router: "Console can see behind this router". The cloud router passes
  the console's status requests (queries on `@/**`) to that router and the
  replies back. The router answers only if its own configuration has
  `adminspace` with read on. On by default for a new router.
- A client: "May read the cloud router's status": every session connected
  to it and its address. Only for the console; off by default.

The registry's table shows it as "Console sees": `behind` for a router,
`reads` for a client.
