# V2.1: connections as lines, not points

Stage V2.1 of the console (plan: the V table, V2.1). Done 2026-10-11 and
checked against the Linux sim, a CRuby node and the MuJoCo rover over
ROS 2 (S1's compose).

Who is on the network (the nodes) is what the graph is read for; which
Zenoh session carries them is needed only when something does not
connect. V2 drew every session as a point between the router and its
nodes. Now the nodes are joined to their router directly, and the old
drawing is one tick away.

## The default drawing

| Element | Drawn as |
|---|---|
| a node and its router (Asterism node, ROS 2 node, this console) | a grey line, labelled with the role of its session: `client` or `peer` (both, `client / peer`, when a node has sessions of both kinds at one router) |
| a session with several nodes (a ROS 2 process: `mujoco_ros2_control_node` carries six) | a line from each node, each labelled (see below) |
| sessions that carry no node (a plain Zenoh client, a tool) | one "N other connections" node per router, joined to it. Its details: role, Zenoh ID and address of each |
| two sessions connected to each other without a router | a dashed blue line between their nodes, labelled `peer` |
| the console's second session (the bridge's reader carries no token) | counted as the console's: one line, both sessions in its details |

Lines to the router are thinner and lighter than topic edges: the topics
are what the drawing is about. A node's details ("Connection") list each
of its sessions: Zenoh ID, role, address, link (tcp, tls, ...), the
certificate name on TLS, the router (a link to it) and the other nodes on
the same session ("Also on it"). Clicking a line shows the same for the
sessions behind it.

### Several nodes on one session: a line each

Two ways were tried on the rover (one process, six nodes):

- **A line from each node** (chosen). The drawing keeps V2's shape: nodes
  where fcose puts them, topic edges between them. The six `peer` labels
  near the router are some clutter; the lines are light so the topics win.
- **A box for the process, one line from the box.** fcose makes the box
  hold every topic edge that ends inside it: on the rover it took two
  thirds of the view and shrank the rest of the drawing until the labels
  could not be read. A box also already means "an Asterism node and its
  apps"; a second kind of box would be read the same way. And turning
  "Sessions as points" on and off would move the nodes in and out of the
  box, which the stable layout cannot keep.

Which nodes share a session is not lost: each line carries `shared` (the
number of nodes on its session), the details of the line say "One session
carries 6 nodes (one process)", and a node's details list the others.

## Toggles

The bar had "Routers and sessions". Now:

- **Routers**: the routers, the router links, and with them every line to
  a router and the "other connections" (the infrastructure layer, as
  before).
- **Sessions as points** (off by default): V2's drawing, each session a
  point between its router and the nodes it carries (dashed lines). The
  lines and "other connections" of the default drawing are hidden. The
  browser remembers the setting (`localStorage`,
  `asterism.console.sessionPoints`; a browser that refuses storage starts
  from the default each time).

The graph rewind of a recording (`/recordings/:id/structure`) has the same
two toggles and draws the same way, recordings made before V2.1 included.

## Where it is built

In the bridge: `Bridge::Connections.apply` (lib/bridge/connections.rb), a
pure function on a graph in to_h form. `Bridge::Graph#to_h` ends with it,
so the live graph, its diffs, the fixture mode and new recordings have the
parts below; `RecordingsController#graph` runs it again on recorded graphs
(it is idempotent: it drops what it added before and adds it again), so a
recording made before V2.1 is drawn the same way. The page only chooses
which parts to show.

Added to the graph:

| Part | |
|---|---|
| `attach` edges | node -> router, one per node and router. `label` the roles, `roles`, `sessions` (Zenoh IDs), `shared`. Also from each "others" node to its router |
| `others` nodes | `others:<router zid>`, layer `infra`, label `N other connections`, data `router`, `sessions` |
| `peer_link` edges | between the nodes of two sessions joined by a `peer_session` edge |
| data `connections` | on every Asterism and ROS 2 node: `zid`, `role`, `address`, `protocol`, `links`, `router`, `router_label`, `cert_name`, `self`, `nodes` |

Sessions, `session` and `carries` edges are unchanged (Sessions as points,
the relay apply's view of the cloud router).

### Peer to peer

The routers' admin space lists the sessions at each router, not the links
peers have among themselves. rmw_zenoh's peers do connect to each other
(gossip), but nothing the bridge reads shows it, so no line is drawn for
them. The one link the bridge knows is its own: `Bridge::Graph.build`
takes `peer_links` (pairs of Zenoh IDs; the bridge passes its session's
`peer_zids`, empty in client mode, which is how the bridge runs), adds a
`peer_session` edge (and a session for a peer no router has), and
`Bridge::Connections` turns it into `peer_link` lines between the nodes.
Tested with made-up IDs; not seen on a live network (the bridge in peer
mode did not start: the same Zenoh configuration goes to its object
layer's session too, which then closed).

## Legend

By the drawing: without "Sessions as points", "Other connections",
"connection to the router (client / peer)" and "peer to peer, no router";
with it, "Session", "session at a router" and "what a session carries".
The counts above the graph do not count the "other connections" node.
