# V4: recording and playback (MCAP)

Stage V4 of the console (plan: "V の続き", the roles of rosbag / `ros2 bag`
and rqt_bag). Done 2026-10-09 with the asterism 0.4.1 checkout, and checked
the same day against a real network: zenohd 1.10.1 and ROS 2 Jazzy
(rmw_zenoh) in docker, rclcpp's talker and listener, an rclpy node
publishing a varying `/cmd_vel` and `/imu`, and a CRuby process putting
MessagePack on Asterism keys.

## What it adds

- **Recordings** (`/recordings`, "Recordings" in the navigation): pick ROS 2
  topics (those in the graph), type Asterism key expressions, tick "the
  network structure", set the limits, start. The bridge subscribes and
  writes one MCAP file until the page stops it or a limit is reached. The
  page shows the progress once a second: messages, messages lost, bytes of
  the maximum, seconds of the maximum, the count per channel.
- **List and inspect**: every recording with its channels, messages,
  duration and size; download the file; upload one (for example from
  `ros2 bag record -s mcap`).
- **Timeline** (a finished recording's page, like rqt_bag): one row per
  channel with its message ticks, a time cursor (click or drag, or "Prev" /
  "Next" message of the selected channel), the selected channel's message
  at the cursor, decoded, with its receive time, source time, sequence and
  size, every channel's message at the cursor in one line each, and a plot
  of numeric fields over the whole recording (several fields and channels
  in one plot; clicking the plot moves the cursor).
- **The network at the cursor** (`/recordings/:id/structure`): the graph page
  in a read-only replay mode, showing the network as it was at a time; a
  slider, "Change" back and forth, and the list of changes (what appeared,
  what left). Positions stay where they were between steps, as on the live
  page, and new nodes flash.
- **Playback**: "in the page only" (the default) moves the cursor at 0.25x /
  1x / 4x and the messages follow; nothing is sent. "To the network" (admins
  only, after a confirmation that names the topics and the message count)
  has the bridge republish the recording from the cursor at the chosen
  speed; the page follows it and can stop it. Each one is a row of the audit
  log, shown on the "Call log" page under "Playbacks to the network".

## The file

One MCAP file per recording (`storage/recordings/<time>-<random>.mcap`,
gitignored), profile `ros2`, written by `MCAP::Writer`: chunks (uncompressed,
written at least once a second and at 768 KB), message indexes after each
chunk, then Data End, the summary (schemas, channels, statistics, chunk
indexes, metadata indexes), summary offsets and the footer, with every CRC.
Times are nanoseconds since the epoch: log_time is when the bridge got the
message, publish_time the source time when the message carries one (the
rmw_zenoh attachment's time; a Zenoh timestamp on an Asterism key), else
the log time.

| Channel | topic | message encoding | schema (name / encoding) | metadata |
|---|---|---|---|---|
| ROS 2 topic | `/cmd_vel` | `cdr` (the bytes as received) | `geometry_msgs/msg/Twist` / `ros2msg`: the .msg and those it uses, concatenated as rosbag2 does | `offered_qos_profiles` (rosbag2's YAML, one entry per publisher, from their liveliness tokens), `topic_type_hash`, `ros_domain` |
| Asterism key | the key (`demo-node/sensors/imu`) | `msgpack` | `asterism/msgpack` / `` (none) | `asterism_key_expr` (what was subscribed) |
| Network structure | `/asterism/graph` | `json` | `asterism/graph` / `jsonschema` | |

ROS 2 messages keep the sequence number of their attachment (as uint32).

**Schemas.** `Bag::MsgDefs` reads the .msg files from `vendor/msgdefs` (the
Jazzy definitions of the common packages, Apache-2.0, see its NOTICE), then
from a ROS 2 install named by `AMENT_PREFIX_PATH`. The dependencies of each
type are taken sorted, depth first, each once, like rosbag2_cpp's
LocalMessageDefinitionSource; the schemas of `sensor_msgs/msg/Imu`,
`geometry_msgs/msg/Twist` and `std_msgs/msg/String` are byte for byte the
ones `ros2 bag record` writes (a test compares them with a file rosbag2
wrote). A type that is not found gets encoding `unknown` and no text, as
rosbag2 writes it.

**The network structure** is the console's own graph (`Bridge::Graph#to_h`,
the same nodes and edges the live page draws): a message
`{"kind": "snapshot", "version", "graph"}` when the recording starts and
again after 30 s of changes, and `{"kind": "diff", "version", "diff"}`
(`Bridge::Graph.diff`: nodes and edges added, removed, changed) on every
change in between. The graph at a time is the last snapshot before it with
the diffs after it applied (`Bag::View#graph_at`).

**Why the Asterism channels have a schema record.** The plan said schema
id 0 for them; rosbag2 refuses such a file as a whole (`ros2 bag info`:
"Could not find schema for topic /asterism/graph"). With a schema record of
their own, `ros2 bag info` lists them (type `asterism/msgpack` and
`asterism/graph`).

## Playback to the network

`Bridge::Player`, on a thread of the bridge: the messages of the chosen
channels in log-time order, each at its time from the start (or from the
cursor) divided by the speed.

- **ROS 2** (cdr channels): an `Asterism::ROS::Node`
  `asterism_console_playback` (one per domain, from the channel's
  `ros_domain`, else 0) with a publisher per topic, declared on the
  bridge's session. Its liveliness tokens (node and publishers) make it a
  ROS 2 node to the others (`ros2 node list` showed `/asterism_console_playback`
  during the playback, `ros2 topic list -v` its publisher of `/cmd_vel`).
  Each message goes out with a new rmw_zenoh attachment: the publisher's
  sequence number, the time it is sent, and the GID derived from its token.
  The payload is the recorded CDR as it is (not decoded, so any type plays).
  The type name comes from the channel's schema name, the type hash from
  its `topic_type_hash` (rosbag2 writes it too), else from the bundled type;
  a channel with neither is not sent, and the page says why. The QoS is the
  first recorded publisher's (reliability, durability, history and depth).
  The tokens are withdrawn when the playback ends.
- **Asterism keys** (msgpack channels): put on the recorded key, payload as
  recorded.
- **Never sent**: the network structure, and any other encoding.
- **Who and how**: `POST /playbacks` needs an admin and `confirm=inject`
  (the page asks first, naming the topics and the number of messages); one
  playback at a time; a request the bridge does not take within 30 s
  expires. The rows (who, when, recording, from where, speed, status,
  messages sent, what was not sent and why) are the audit log.

## Limits and costs

| | Bound |
|---|---|
| A recording | at most 512 MB and 3600 s (defaults 64 MB, 300 s, set per recording); the message that would pass the size is not written; past the time no message is written |
| Recordings | 2 at once; all files together `ASTERISM_RECORDINGS_MAX_BYTES` (4 GB); 32 topics and 16 keys each |
| Uploads | 256 MB |
| A recording's subscriptions | queue depth 1024 (asterism-zenoh's maximum; the default of 16 is 0.3 s of a 50 Hz topic); what is dropped anyway is counted as lost |
| Timeline | 2000 tick buckets per channel; a plot reads at most 5000 messages of a channel (evenly spaced); arrays in a shown message cut at 256 elements; the 4 most recently opened files' indexes kept per Puma process |

Measured on this PC (Ruby 3.2, a synthetic recording of 100000
`sensor_msgs/msg/Imu`, 324 bytes each, 36 MB):

| | |
|---|---|
| `Bridge::Recorder#ros` (on the receiving thread: attachment, channel lookup, writing into the chunk) | 8.1 us per message |
| Opening the file and reading its index (summary and message indexes, no message read) | 87 ms |
| The message of a channel at a time, decoded | 47 us |
| A plot of one field (5000 of the 100000 messages read and decoded) | 102 ms |
| The ticks (1000 buckets) | 5 ms |
| Reading every message (`each_message`) | 171 ms |

So a 1 kHz topic costs the bridge under 1 % of a core to record. As with the
rates and plots, the real cost is the traffic: every message of a recorded
topic reaches the bridge (over a relay, across it), and the file grows with
it (the live check: 2080 messages, 22 KB/s).

## Found on the way

- **rosbag2 and schemaless channels**: a channel with schema id 0 makes
  `ros2 bag info` refuse the whole file; `ros2 bag play` also refuses a
  file whose channels are not all CDR, even when told to play some topics
  only. Hence the Asterism channels' schema records and the "ROS 2 topics
  only" download (above).
- **A subscription's queue is 16 samples** by default in asterism-zenoh,
  0.3 s of a 50 Hz topic. The first live recording had two gaps of 0.3 and
  0.5 s in every channel at once. The recordings now subscribe with depth
  1024 and count what is still dropped. The second recording had the same
  kind of gaps with nothing lost and receive delays under 4 ms: the source
  times of every publisher (the rclpy node in the container and the CRuby
  one on the host) skip the same instants, so these were moments the whole
  machine stood still (the publishers' timers skipped them), not losses.
- **The time limit** was only checked twice a second, so a 28 s recording
  ran 29.2 s; the recorder now refuses messages past the limit itself.
- **Times in the page**: nanoseconds since the epoch do not fit a
  JavaScript number exactly (1.79e18 > 2^53), and stepping to the next
  message needs its exact time; the timeline's endpoints take and give
  times as offsets from the first message.
- **`/rosout` in `ros2 bag record`** replays its transient-local history: two
  seconds of recording held 1014 old log lines. The test fixture leaves
  `/rosout` out. (The console's recordings take only what comes while they
  run.)
- **Playing `/rosout` back** republishes old log lines under the playback
  node, as `ros2 bag play` does. The page plays every channel (choosing
  them is not done yet, see below), so leave `/rosout` out of a recording
  meant for playback, or play the ROS 2 copy with `ros2 bag play --topics`.
- **asterism 0.4.1** (committed meanwhile by another stage) bundles
  `nav_msgs`, so two console tests that used `nav_msgs/msg/Odometry` as "not
  bundled" now use `shape_msgs/msg/Mesh`. `Gemfile.lock` records 0.4.1 (the
  checkout's version).

## Not done

- zstd and lz4 chunks (no decompressor in Ruby's standard library; a pure
  Ruby zstd decoder would be the way). The console writes uncompressed
  chunks only.
- Choosing channels for a playback in the page (the API takes `channels`;
  the page sends all), and a loop.
- MCAP attachments and metadata records are read but not shown.
- ROS 2 services are not recorded (rosbag2 can record service events).
- The `rosbag2` metadata record (ROS distribution, per-topic counts) is not
  written; `ros2 bag info` does without it.
- A recording does not go on across the bridge losing its router: it is
  finished there (stop reason "the bridge stopped (or lost its router)").
  A bridge that crashes leaves a file without a summary; the next bridge
  gives it one (`Bag::Repair`), losing at most the last second.
